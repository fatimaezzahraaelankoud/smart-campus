## Sprint 1 - rôle tenu : chef de projet

### Décision 2026-11-05 : gateway Spring Cloud Gateway (réactive) avec Spring Security WebFlux
- Contexte : point d'entrée unique qui valide les JWT, route, limite les accès et protège les chemins internes.
- Options étudiées : (A) Spring Cloud Gateway réactive ; (B) Gateway MVC (servlet) ; (C) un reverse proxy Nginx.
- Décision : A. Les routes, filtres globaux et le support SSE de la notification-service (Sprint 2) y sont natifs.
  La bibliothèque `common` garde ses dépendances web optionnelles pour cohabiter avec cette pile réactive.
- Conséquences : tests avec `WebTestClient` ; le code servlet de `common` (filtre, gestionnaire d'erreurs) n'est actif
  que dans les autres services, la gateway a ses équivalents (`RequestSanitizingFilter`, `GatewayErrorHandler`).

### Décision 2026-11-05 : en-têtes X-User-* posés uniquement par la gateway
- Contexte : les services ont besoin de l'identité pour les journaux et la limitation de débit.
- Options : faire confiance aux en-têtes envoyés par le client ; ou les supprimer à l'entrée et les poser après
  validation du JWT.
- Décision : suppression systématique à l'entrée puis pose après validation. Les services re-valident quand même
  le JWT (défense en profondeur).
- Conséquences : un test vérifie qu'un client ne peut pas forger `X-User-Role`.

### Décision 2026-11-05 : chemins /internal/** et Actuator bloqués en 404 avant Spring Security
- Décision : filtre en tête de chaîne : même un administrateur authentifié ne peut pas appeler `/internal/**`.
- Conséquences : les appels service à service passent par le réseau du cluster, jamais par la gateway.
